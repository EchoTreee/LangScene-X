# 部署过程中遇到的问题

## 1. 文档目的

本文档总结 `LangScene-X` 在当前机器上的实际部署过程，重点说明以下问题：

- NVIDIA Blackwell 架构与当前 PyTorch 版本的兼容冲突
- 项目内本地 CUDA 扩展的编译和运行时问题
- README 中未覆盖的依赖缺失与脚本问题
- 最终可工作的环境形态和推荐启动方式

当前部署机器的重要环境特征：

- GPU：`NVIDIA RTX PRO 6000 Blackwell Max-Q Workstation Edition`
- 驱动：`595.45.04`
- `nvidia-smi` 报告 CUDA 版本：`13.2`
- Python 环境：`/workspace/miniconda3/envs/langscenex`
- Python 版本：`3.10.19`

---

## 2. 核心冲突：Blackwell 架构与 PyTorch/CUDA 扩展

### 2.1 现象

部署初期，环境中的 PyTorch 版本是：

- `torch 2.5.1`
- `torchvision 0.20.1`

在导入和运行涉及 CUDA 的模块时，PyTorch 明确给出告警：

- 当前 GPU 的 CUDA capability 是 `sm_120`
- 当前 PyTorch 仅支持到 `sm_90`
- 即当前 PyTorch 版本没有针对 Blackwell 架构的正式编译支持

表现为：

- `torch.cuda.is_available()` 返回 `True`
- GPU 名称可以识别
- 但任何需要严格依赖架构适配的 CUDA 编译或运行，都存在不稳定和不兼容风险

### 2.2 根因

Blackwell 是更新一代的 NVIDIA 架构，而当前环境中的 `torch 2.5.1` 对应的官方 CUDA 构建并不包含 `sm_120`。

这带来两类问题：

1. 运行期问题
- PyTorch 虽能看到 GPU，但不代表对应架构已经正式支持
- 一些 CUDA kernel 可能退化、失败，或者在编译自定义扩展时暴露更多问题

2. 编译期问题
- 项目中的本地 CUDA 扩展依赖 `torch.utils.cpp_extension`
- 扩展构建时会同时依赖：
  - PyTorch 头文件与 ABI
  - 可用的 `nvcc`
  - 合适版本的 GCC/G++
  - 完整的 CUDA 开发头文件
- 当 GPU 架构过新、PyTorch 过旧时，整个链路更容易失配

### 2.3 结论

这是部署过程中最核心的技术冲突：

- 机器硬件是 Blackwell（`sm_120`）
- 项目当前实际跑通时仍依赖 `torch 2.5.1`
- 这套组合可以让项目的大部分依赖导入成功，但不属于“官方完整支持 Blackwell”的理想状态

## 3. 本地 CUDA 扩展的主要冲突

项目 README 里要求安装两个关键本地扩展：

- `field_construction/submodules/simple-knn`
- `field_construction/submodules/diff-langsurf-rasterizer`

这两个扩展是部署过程中最难处理的部分。

### 3.1 首轮安装失败：build isolation 下找不到 torch

初次执行：

- `pip install -e field_construction/submodules/simple-knn`
- `pip install -e field_construction/submodules/diff-langsurf-rasterizer`

失败原因是：

- `pip` 默认启用 build isolation
- 隔离构建环境里没有已安装的 `torch`
- 扩展的 `setup.py` 在构建阶段直接 import `torch`

报错特征：

- `ModuleNotFoundError: No module named 'torch'`

#### 解决方法

改为禁用 build isolation：

```bash
pip install --no-build-isolation -e field_construction/submodules/simple-knn
pip install --no-build-isolation -e field_construction/submodules/diff-langsurf-rasterizer
```

---

### 3.2 第二轮失败：找不到 nvcc

禁用 build isolation 后，构建继续推进，但很快失败：

- 构建脚本默认寻找 `/usr/local/cuda/bin/nvcc`
- 当前机器该路径不存在

报错特征：

- `No such file or directory: '/usr/local/cuda/bin/nvcc'`

#### 根因

系统上虽然有 NVIDIA 驱动，也有多个 conda 环境，但标准系统路径下没有完整 CUDA toolkit。

#### 排查结果

后续发现：

- `langscene124` 环境中存在可用 `nvcc`
- `langscenex` 环境里也已经有大量 CUDA 12.4 相关开发头文件和库

---

### 3.3 第三轮失败：GCC 版本过高

当构建链路能找到 `nvcc` 后，又出现新的问题：

- `langscenex` 环境内的 conda 编译器是 GCC 15.2
- 当前 `nvcc`（12.4 系）不支持这么新的 GCC

报错特征：

- `unsupported GNU version! gcc versions later than 13 are not supported`

#### 解决方法

显式改用系统编译器：

- `CC=/usr/bin/gcc`
- `CXX=/usr/bin/g++`

系统编译器版本为：

- `gcc 11.4.0`
- `g++ 11.4.0`

这符合 `nvcc` 的支持区间。

---

### 3.4 第四轮失败：CUDA 头文件缺失

即使找到了 `nvcc` 和合适的 GCC，构建仍然失败，错误包括：

- `cub/cub.cuh: No such file or directory`
- `nv/target: No such file or directory`
- `cuda/std/type_traits: No such file or directory`
- `cudafe++: not found`

#### 根因

使用“只有 `nvcc` 可执行文件”的路径并不足够，扩展构建需要完整 toolkit：

- `nvcc`
- `cudafe++`
- `ptxas`
- CUDA include 目录
- CUB/CCCL
- NVVM 等辅助组件

#### 最终解决方法

最终采用的是一套混合但稳定的方案：

1. 使用 `langscene124` 里的完整 CUDA 工具链二进制
- 提供完整 `nvcc`、`cudafe++` 等工具

2. 同时使用 `langscenex` 中现成的 CUDA 头文件
- `targets/x86_64-linux/include`
- `include`

3. 显式指定编译环境变量

实际编译时使用的核心变量如下：

```bash
CUDA_HOME=/workspace/miniconda3/envs/langscene124
PATH=/workspace/miniconda3/envs/langscene124/bin:$PATH
LD_LIBRARY_PATH=/workspace/miniconda3/envs/langscene124/lib:$LD_LIBRARY_PATH
CPATH=/workspace/miniconda3/envs/langscenex/targets/x86_64-linux/include:/workspace/miniconda3/envs/langscenex/include
CC=/usr/bin/gcc
CXX=/usr/bin/g++
TORCH_CUDA_ARCH_LIST='9.0+PTX'
```

在这组参数下，两个扩展最终都成功编译：

- `simple_knn`
- `diff_LangSurf_rasterization`

---

### 3.5 运行期问题：simple_knn 缺少 libc10.so

扩展编译成功后，并不意味着立即能导入。

`simple_knn._C` 在运行时又暴露问题：

- `ImportError: libc10.so: cannot open shared object file`

#### 根因

`simple_knn` 运行时依赖 PyTorch 自带共享库：

- `libc10.so`
- 位于 `torch/lib`

但默认 `LD_LIBRARY_PATH` 没有包含该目录。

#### 解决方法

最终没有继续依赖脆弱的 conda hook，而是在项目根目录加入了一个显式环境脚本：

[langscenex_env.sh](/workspace/projects/LangScene-X/langscenex_env.sh)

当前脚本内容的作用很单一：

- 将 `torch/lib` 加入 `LD_LIBRARY_PATH`

推荐使用方式：

```bash
conda activate langscenex
source /workspace/projects/LangScene-X/langscenex_env.sh
```

这样可稳定导入：

- `simple_knn._C`
- `diff_LangSurf_rasterization._C`

## 4. 预编译产物为何不能直接复用

项目仓库内其实已经带有部分 `.so` 文件，但它们不能直接作为最终解法。

### 4.1 simple-knn

仓库内存在：

- `field_construction/submodules/simple-knn/simple_knn/_C.cpython-310-x86_64-linux-gnu.so`

它在补齐运行时库路径后可以被导入，但这并不能代表部署已经完成，因为：

- 仍需要稳定的环境路径管理
- 后续其他扩展仍未解决

### 4.2 diff-langsurf-rasterizer

仓库内也有预编译 `.so`，但直接导入时报错：

- `undefined symbol: _ZNK3c1011StorageImpl27throw_data_ptr_access_errorEv`

#### 根因

这是典型的 PyTorch ABI / C++ 符号不匹配：

- 该二进制并非针对当前环境中的 `torch` 构建
- 即使 Python 版本一致，也不能保证 C++ 符号兼容

#### 结论

`diff-langsurf-rasterizer` 必须在当前环境里重新编译，不能直接复用仓库附带产物。

## 5. 科学计算栈的兼容问题

### 5.1 TensorFlow 与 NumPy 2.x 冲突

早期安装第三方依赖时，环境里一度出现：

- `numpy 2.x`
- `tensorflow 2.15.0`

这会导致 TensorFlow 导入失败，报错特征为：

- `All ufuncs must have type numpy.ufunc`

#### 根因

`tensorflow 2.15.0` 与 `numpy 2.x` 不兼容。

#### 解决方法

将 NumPy 固定回 `1.26.4`，同时配套重装相关科学计算包：

- `numpy==1.26.4`
- `scipy==1.14.1`
- `scikit-learn`

最终 TensorFlow 可正常导入。

---

### 5.2 OpenCV / Open3D 与 libGL 问题

在无桌面服务器环境下，最初导入时报错：

- `cv2`: `libGL.so.1: cannot open shared object file`
- `open3d`: 同样受 OpenGL 运行时影响

#### 解决方法

1. 卸载 GUI 版 OpenCV
- 移除 `opencv-python`

2. 改用 headless 版本
- 安装 `opencv-python-headless==4.10.0.84`

3. 额外安装 conda 用户态 OpenGL 运行时
- `conda install -n langscenex -y libgl`

完成后：

- `cv2` 可正常导入
- `open3d 0.19.0` 可正常导入

## 7. 项目脚本与代码中的实际问题

除了环境冲突，项目本身还存在几处会直接影响试跑的代码问题。

### 7.1 quick_start.sh 的纯文本未注释

原脚本中有一行：

- `RGB video interpolation`

它不是注释，shell 会把它当命令执行。

#### 解决方法

已将相关说明文字修为注释。

---

### 7.2 quick_start.sh 中 CogVideo 目录名不正确

原脚本写的是：

- `./CogVideo-X`

但实际更合理的目录命名应为：

- `./CogVideoX-ft`

否则 `diffusers` 会将 `./CogVideo-X` 当作非法 Hugging Face repo id 处理。

#### 解决方法

已修正 [quick_start.sh](/workspace/projects/LangScene-X/quick_start.sh) 中的默认路径。

---

### 7.3 get_normal.py 使用作者机器上的绝对缓存路径

原代码中硬编码：

- `/home/lff/bigdata1/cjw/model_cache`

这显然是作者本地机器路径，导致在当前机器上调用 StableNormal 时失败。

#### 解决方法

已将 [get_normal.py](/workspace/projects/LangScene-X/get_normal.py) 改为使用当前用户目录下的本地缓存：

- `~/.cache/langscenex_models`

这让代码变为可移植状态。

## 8. quick_start 实际试跑得到的结论

在当前环境下，`quick_start.sh` 已实际执行过一次烟雾测试。

### 8.1 已经排除的环境问题

以下问题已经被解决：

- Python 环境和依赖缺失
- TensorFlow / OpenCV / Open3D 导入问题
- 本地 CUDA 扩展的编译与导入问题
- 脚本中的明显 shell 语法错误
- 代码中的作者本地绝对路径问题

### 8.2 当前真正的阻塞点

`quick_start.sh` 目前停在模型资源层面，而非环境层面，具体包括：

1. 缺少 SAM2 权重
- `./sam2_hiera_large.pt`

2. 很可能也缺少 SAM1 权重
- `./sam_vit_h_4b8939.pth`

3. 缺少 CogVideoX 模型目录
- `./CogVideoX-ft`

4. 分割和视频插值前序失败后，会连锁导致：
- `demo/seg/colors.npy` 缺失
- 后续 3DGS 场构建阶段无法继续

#### 结论

当前试跑失败的主要原因是：

- 模型权重/模型目录还没有下载到项目要求的位置

而不是环境本身没有部署好。

## 9. 最终可工作的环境结论

### 9.1 当前推荐使用方式

```bash
conda activate langscenex
source /workspace/projects/LangScene-X/langscenex_env.sh
```

在该方式下，已经验证可正常导入：

- `numpy 1.26.4`
- `tensorflow 2.15.0`
- `cv2 4.10.0`
- `open3d 0.19.0`
- `simple_knn._C`
- `diff_LangSurf_rasterization._C`

### 9.2 当前 PyTorch 状态

最终环境保留在：

- `torch 2.5.1`
- `torchvision 0.20.1`

原因是：

- 我曾尝试升级到支持 Blackwell 的 `torch 2.11.0+cu128`
- 但该升级涉及大量 NVIDIA 运行时大包下载，耗时极长
- 在尚未完成前，为避免破坏当前已稳定工作的环境，已停止后台升级任务

### 9.3 对 Blackwell 的现实判断

当前环境的状态应理解为：

- 项目依赖已经基本跑通
- 项目本地 CUDA 扩展已能构建与导入
- 但 PyTorch 对 Blackwell 的正式架构支持仍未完成升级

也就是说：

- 当前环境已经是“可部署、可继续调试项目”的状态
- 但还不是“针对 Blackwell 最优、最官方”的终态环境

## 10. Blackwell 正式迁移建议

上文记录的是旧环境如何被修到“基本可用”，但它依然混用了旧版 PyTorch 与旧工具链。对于 Blackwell 机器，更稳的终态迁移路线应当是：

1. 保留旧 `langscenex` / `langscene124` 作为回退，不再继续污染它
2. 新建独立的 `langscenex_bw` 环境，并安装官方 `cu128` PyTorch wheel
3. 先验证最小 CUDA 张量运算，再安装项目依赖
4. 在这套新环境里重新编译 `simple-knn` 和 `diff-langsurf-rasterizer`
5. 最后再运行项目入口

仓库根目录已新增 [BLACKWELL_MIGRATION.md](/workspace/projects/LangScene-X/BLACKWELL_MIGRATION.md)，给出了可直接复制执行的命令顺序。

需要特别避免的点：

- 不要再把 `langscene124` 当成 Blackwell 的最终编译链来源
- 不要在 PyTorch 运行时尚未通过最小 GPU 测试前就开始排查扩展
- 不要复用旧 `.so`，升级 `torch` 后必须在当前环境里重编

## 12. 一句话总结

本次部署中最大的技术冲突不是 Python 包本身，而是：

- Blackwell 架构过新
- 当前 PyTorch 版本较旧
- 项目依赖两个需要本地编译的 CUDA 扩展
- 项目脚本和代码里还夹杂了若干作者本地环境假设

最终通过以下手段把环境落到了可工作状态：

- 禁用 build isolation
- 使用完整 CUDA 工具链 + 系统 GCC 11 重编本地扩展
- 固定 `numpy/scipy` 版本
- 改用 headless OpenCV 并补 `libgl`
- 额外补安装运行时缺失依赖
- 修复 `quick_start.sh` 和 `get_normal.py` 中的项目自身问题
- 用 [langscenex_env.sh](/workspace/projects/LangScene-X/langscenex_env.sh) 解决 `simple_knn` 的运行时库路径问题

当前剩余阻塞已经从“环境冲突”收敛为“模型权重未就位”。
